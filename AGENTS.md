# AGENTS.md — ImGuiWasm

## Build & Run

### Rust Core

```bash
cd imgui-wasm-core
cargo build
```

### C++ Wrapper & Example

```bash
cmake -S . -B build
cmake --build build
```

Run the example from the repository root:

```bash
LD_LIBRARY_PATH=target/debug ./build/imgui-wasm-cpp/example_cpp [bind_address]
```

Then open `http://127.0.0.1:8888`.

### Python Example

Build `imgui-wasm-core` first, then run:

```bash
PYTHONPATH=imgui-wasm-python python3 imgui-wasm-python/examples/example.py
```

## Project Structure

| Component | Path | Description |
|-----------|------|-------------|
| **imgui-wasm-core** | `imgui-wasm-core/` | Rust core library: HTTP/WebSocket server, binary protocol, C ABI, embedded frontend, and internal Dear ImGui web backend. |
| **C lifecycle API** | `imgui-wasm-core/include/imgui_wasm.h` | Small public lifecycle API: `imgui_wasm_init`, `imgui_wasm_shutdown`, `imgui_wasm_new_frame`, `imgui_wasm_render`. |
| **Generated ImGui API** | `imgui-wasm-core/include/imgui_wasm_imgui.h` | Separate `dear_bindings`-generated Dear ImGui C API surface. Do not include this from `imgui_wasm.h`. |
| **imgui-wasm-cpp** | `imgui-wasm-cpp/` | Thin C++ convenience wrapper. It should not own backend internals or duplicate Dear ImGui runtime code. |
| **imgui-wasm-python** | `imgui-wasm-python/` | Python package: handwritten lifecycle wrapper plus generated `ctypes` ImGui API. |
| **Call-stream capture** | `imgui-wasm-core/include/imgui_wasm_capture.hpp` | Internal generated wrappers that transparently capture supported application `ImGui::` calls. |
| **WASM replay twin** | `imgui-wasm-core/wasm/` | Browser-side Dear ImGui compiled via Emscripten on every Cargo build; it replays captured calls to regenerate draw data locally. |
| **Call-stream artifacts** | `imgui-wasm-core/tools/generated/`, `imgui-wasm-core/include/imgui_wasm_opcodes.h` | Generated opcode table, arg schema, replay switch, and patch specs. Regenerated by `generate_bindings.py`. |

## Architecture

1. **Rust core** (`imgui-wasm-core`) owns transport, server state, binary serialization, compression, frame hashing, delta frames, and browser-facing messages.
2. **Internal ImGui backend** (`imgui-wasm-core/src/imgui_backend.cpp`) owns the Dear ImGui context and bridges input/frame/render work into Rust through `imgui_wasm_internal.h`.
3. **Public lifecycle API** (`imgui_wasm.h`) stays small and language-neutral. Users call init/shutdown/new_frame/render only.
4. **Generated ImGui API** is separate. `imgui-wasm-python/tools/generate_bindings.py` emits both Python `ctypes` bindings and Rust `imgui_wasm_ig*` export forwarders.
5. **Language bindings** should be thin. They should call the lifecycle API and generated ImGui API instead of reimplementing backend logic.
6. **Browser frontend** (`imgui-wasm-core/frontend`) renders draw commands via WebGL.
7. **Multi-client**: each WebSocket client is assigned a unique `u32` client ID. Per-client state includes display size, delta/frame tracking, and clipboard. Input from any client drives the shared ImGui context; the most recently active client determines the display size.

## Generated API Rules

- Do not handwrite broad ImGui API wrappers in C++, Python, or Rust.
- Python lifecycle code is handwritten in `imgui-wasm-python/imgui_wasm/core.py`.
- Python ImGui API code is generated in `imgui-wasm-python/imgui_wasm/imgui.py`.
- Rust dynamic-library exports for generated ImGui calls are generated in `imgui-wasm-core/src/generated_imgui_api.rs`.
- Regenerate both outputs with:

```bash
python3 imgui-wasm-python/tools/generate_bindings.py
```

- The generator consumes metadata from `imgui-wasm-core/tools/dear_bindings/`.
- Generated public ImGui export names use the `imgui_wasm_ig*` prefix so dynamic FFI languages can load them reliably from `libimgui_wasm`.
- Keep `imgui-wasm-core/include/imgui_wasm.h` lifecycle-only. Keep generated ImGui declarations in `imgui-wasm-core/include/imgui_wasm_imgui.h`.

## Key Gotchas

- **Shared Library Name**: the Rust crate is named `imgui_wasm`, producing `libimgui_wasm.so` on Linux, `libimgui_wasm.dylib` on macOS, or `imgui_wasm.dll` on Windows.
- **Static Library Name**: C++ builds may link `target/debug/libimgui_wasm.a` or `target/release/libimgui_wasm.a` so users share the same Dear ImGui runtime.
- **Dear ImGui Fetch**: `imgui-wasm-core/build.rs` clones Dear ImGui into `imgui-wasm-core/third_party/imgui` if missing. This directory is local dependency state and should not be committed.
- **Generated binding files**: `imgui-wasm-core/include/imgui_wasm_imgui.h`, `imgui-wasm-core/src/imgui_wasm_imgui.cpp`, and `imgui-wasm-core/tools/dear_bindings/*.json` are committed generated inputs/outputs used by language bindings.
- **Frontend changes**: changes under `imgui-wasm-core/frontend/*` require `cd imgui-wasm-core && cargo build` to re-embed.
- **ImDrawIdx normalization**: Rust core widens indices from 16-bit to 32-bit for the protocol.
- **Frame hash determinism**: `hash_draw_list` (`imgui-wasm-core/src/state.rs`) uses **xxh3** (`xxhash-rust`, `xxh3` feature) and its `u32` digest drives delta-frame detection (`DeltaState.last_frame_hash`, per-list hashes). The hash MUST be deterministic across frames and runs. Do not swap in a randomized hasher (`ahash` with a random seed, or `std::collections::hash_map::RandomState`) without a fixed key — otherwise delta detection thrashes and every frame is re-sent in full.
- **OES_element_index_uint**: required for WebGL 1 contexts.
- **Local-only directories**: do not commit `build/`, `target/`, `.venv/`, `third_party/`, or `imgui-wasm-core/third_party/`.

## Binary Protocol

All values are little-endian. First byte is message type.

### Server-to-client messages

- `0x01` = Full frame: header with display pos/size/scale and list count, then per-list vertex/index/cmd data.
- `0x02` = Texture: id (`u64`), width, height, pixel data length, RGBA pixels.
- `0x03` = LZ4-compressed full frame: uncompressed length (`u32`) plus LZ4 block data.
- `0x04` = Delta frame: full-frame header plus changed-list count, then per changed list.
- `0x05` = LZ4-compressed delta frame.
- `0x06` = Client ID assignment: assigned client id (`u32`). Sent once on WebSocket connect before any other messages.
- `0x18` = Clipboard text: text length (`u32`), UTF-8 text bytes.

### Client-to-server messages

All client messages include a `u32` client ID at offset 1 (after the message type byte).

- `0x10` + client_id (`u32`) + x (`f32`) + y (`f32`) = Mouse move.
- `0x11` + client_id (`u32`) + button (`u8`) = Mouse down.
- `0x12` + client_id (`u32`) + button (`u8`) = Mouse up.
- `0x13` + client_id (`u32`) + dx (`f32`) + dy (`f32`) = Mouse wheel.
- `0x14` + client_id (`u32`) + key (`u16`) = Key down.
- `0x15` + client_id (`u32`) + key (`u16`) = Key up.
- `0x16` + client_id (`u32`) + character (`u32`) = Text input.
- `0x17` + client_id (`u32`) + w (`f32`) + h (`f32`) = Resize.
- `0x18` + client_id (`u32`) + text length (`u32`) + UTF-8 text = Clipboard text from client.

### Call-stream transport (alternative to draw-data)

When `imgui_wasm_config_t.transport == IMGUI_WASM_TRANSPORT_CALLSTREAM`, the server streams the sequence of ImGui API calls instead of rendered draw data. The browser replays them against a WASM-compiled Dear ImGui twin to regenerate draw data locally. This drops per-frame bandwidth from KB of vertices to tens of bytes of calls, and idle frames cost ~nothing.

**Host integration:** C++ hosts use the ordinary Dear ImGui `ImGui::` API in
both transports. `imgui_wasm.hpp` transparently redirects supported rendering
calls through the internal capture surface. Getters, queries, and unsupported
calls retain their native/server-side implementations. Python hosts continue
to use the generated `ig*` ABI internally.

**Additional server-to-client messages (call-stream mode):**

- `0x07` = Call-stream frame: header (6 × `f32`: dpx,dpy,dsw,dsh,fbsx,fbsy) + `frame_id` (`u32`) + `call_count` (`u32`, hint; may be 0 = unknown) + opcoded calls. Each call: `opcode` (`u16`) + args per the schema in `imgui-wasm-core/tools/generated/callstream_schema.json`.
- `0x08` = LZ4-compressed call-stream frame: `uncompressed_len` (`u32`) + LZ4 block data (same layout as `0x03`/`0x05`).
- `0x09` = String-table update: `count` (`u32`) + `count` × { `id` (`u32`), `len` (`u32`), UTF-8 bytes }. Sent on connect (full table replay) and whenever new strings are interned.

**WASM twin build:** every `cargo build` requires Emscripten (`emcc` on PATH,
or set `IMGUI_WASM_EMCC`) and rebuilds
`imgui-wasm-core/wasm/imgui_wasm_replay.{wasm,js}` for embedding in the server.

## Open Source Hygiene

- Keep `LICENSE`, `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, and `THIRD_PARTY_NOTICES.md` current when changing distribution behavior.
- ImGuiWasm is MIT licensed. Generated dear_bindings/Dear ImGui-derived files have upstream MIT notices that must remain preserved.
- Package metadata should keep license and repository URLs in sync:
  - `imgui-wasm-core/Cargo.toml`
  - `imgui-wasm-python/pyproject.toml`

## After Editing

1. If you edited `imgui-wasm-core/frontend/*`, run `cd imgui-wasm-core && cargo build`.
2. If you edited `imgui-wasm-core/src/*`, `imgui-wasm-core/include/*`, or generated ImGui API files, run `cd imgui-wasm-core && cargo build`.
3. If you edited `imgui-wasm-cpp/*`, run `cmake --build build`.
4. If you edited Python files, run `python3 -m compileall imgui-wasm-python/imgui_wasm imgui-wasm-python/examples`.
5. If you edited binding metadata or generator code, run `python3 imgui-wasm-core/tools/dear_bindings/generate.py`, then rebuild core and compile Python.
6. If you edited `imgui-wasm-core/wasm/*`, the opcode header, or generated replay switch, run `cargo build` to regenerate the embedded WASM twin.
7. Verify end-to-end when behavior changes: run an example and open `http://127.0.0.1:8888`. For call-stream mode, build the call-stream example (`cmake -DIMGUI_WASM_BUILD_EXAMPLES=ON --build build`) and run `./build/example_cpp_callstream`.
